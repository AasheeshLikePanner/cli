## Missing from the spec

**2. Schema is incomplete.**

`PromptEntry` in the implementation is missing three fields from the agreed design:

```go
// Not in your implementation:
TokenCount          int    `json:"token_count"`
ParentCheckpointID  string `json:"parent_checkpoint_id,omitempty"`
SubagentDepth       int    `json:"subagent_depth"`
```

`TokenCount` especially — it's zero-cost since `CommittedMetadata` already has it, and it's one of the more useful metadata fields for the team visibility roadmap they've talked about publicly.

**3. `ReviewPrompt` indexing — verify it's actually wired.**

`CommittedMetadata.ReviewPrompt` needs to be read when `Kind == "agent_review"` and used as the `PromptText`. The doc says it's there but doesn't show the builder code for this path. Double-check this actually runs, not just compiles.

**4. Unicode NFC normalization is likely missing.**

The tokenizer does `strings.ToLower` but the proposal requires NFC normalization before that so `"café"` and `"cafe\u0301"` hash to the same tokens. Add:

```go
import "golang.org/x/text/unicode/norm"
normalized := norm.NFC.String(strings.ToLower(text))
```

**5. Query guard for special characters and minimum length.**

`ParseQuery` needs two things that probably aren't there:
```go
// Strip regex metacharacters before tokenizing
query = specialCharRe.ReplaceAllString(query, " ")

// Minimum length check
if len(strings.TrimSpace(query)) < 2 {
    return nil, errors.New("query too short — enter at least one word")
}
```
Without the special char strip, a query like `"fix $auth"` could panic or return zero results with no explanation.

**6. `--json` PII warning to stderr.**

When `--json` is used in a non-TTY (piped to a file, CI, etc.), write to stderr:
```go
if cfg.JSON && !term.IsTerminal(int(os.Stdout.Fd())) {
    fmt.Fprintln(os.Stderr, "warning: --json output includes full prompt text")
}
```
Small thing but shows you thought about security.

**7. `CommitHash` population — confirm the timing.**

The PostCommit hook fires after the commit lands. Confirm that when you call `git rev-parse HEAD` at that point, you're getting the commit that contains the checkpoint trailer, not the previous commit. If the hook fires before HEAD advances, `CommitHash` will be wrong on every entry. Add a test that asserts `CommitHash != ""` after a commit.

**8. `IndexPath()` for decoupled repos.**

**10. Windows path normalization in `FilesTouched`.**

When writing entries on Windows, normalize to forward slashes:
```go
for i, f := range entry.FilesTouched {
    entry.FilesTouched[i] = filepath.ToSlash(f)
}
```

**The Known Limitations section is a bug list in disguise.**

## The 12 remaining lint errors

You wrote "style/safe-errors" next to them. A senior engineer reads past that framing:

**The 4 `errcheck` issues where you're using `_` are not safe.** In Go, silently discarding errors is almost never truly safe. The question is: *which* errors are you discarding? If it's `lock.Unlock()`, that's a real bug — a failed unlock means the next write waits forever for a lock that never releases. If it's a file close after a write, you could be silently losing data. Each one needs to be looked at individually and either properly handled or explicitly documented with a comment explaining why it truly cannot fail.

**The `unused function`** is dead code in the PR. That tells the reviewer the architecture is incomplete — something was planned and not finished, or something was replaced and the old version wasn't cleaned up. Either way it's a signal.

**`revive` in a public OSS repo** usually means exported functions without godoc comments. Every exported function in a Go package needs a comment. This isn't style preference, it's Go convention and `godoc` will show blank entries without it.

Fix all 12 before opening. None of them should take more than an hour.

## The benchmark gap

You ran `BenchmarkSearch1K` at 5.6ms — good result. But the proposal promised targets for both 1K and 10K, and the more important metric you didn't measure is **index load time**, which is on the critical path of every single search command invocation. A 200ms index load at 10K entries means the CLI feels sluggish even when search itself is fast. Add:

```go
BenchmarkIndexLoad1K(b *testing.B)
BenchmarkIndexLoad10K(b *testing.B)
BenchmarkSearch10K(b *testing.B)
BenchmarkIndexAppend(b *testing.B)   // single entry append with lock
```

Also — 1.27 MB memory and 23K allocations per search op on 1K entries. At 100K entries that's 127 MB held in memory for the duration of every search. Not a blocker but a senior engineer will ask about it. Either add a comment in the code acknowledging the tradeoff, or add a note in the PR description. Silence on this looks like you didn't notice.

## The unverified integration points

Three things you built but haven't confirmed work end-to-end:

**`CommitHash` timing.** Your PostCommit hook calls `git rev-parse HEAD`. In a hook that fires after a commit, HEAD should be the new commit — but confirm this by logging the hash and checking it matches the commit that has the checkpoint trailer. One bad assumption here means every entry in the index has the wrong commit hash.

**`ReviewPrompt` path.** You listed it as "not fully verified." **Decoupled repo `IndexPath`.** The proposal calls for `IndexPath()` to read the checkpoint store config when checkpoints are in a separate repo. Is this in `store.go`?
